# Release: this machine's specifics

The procedure is `compound-v:release`. On this machine:

- **A repository Sugarhouse has set up** (it has an `rc` branch): feature PRs into `rc` carry no version bump. A plugin repository gets one bump PR into `rc` just before the cut (`sugar release` refuses a changed plugin without one), and a hotfix that changes the plugin carries its bump in a PR into `hotfix`; otherwise the release picks the version from the conventional-commit subjects, or takes `--version X.Y.Z`. Cut one when the user asks or the sprint's plan says so, with `sugar release OWNER/REPO`, which opens the release PR into `main`; the user merges it with a merge commit, and Sugarhouse tags, builds and installs it on both machines. Follow it with `sugar release status`; `sugar release withdraw ID` abandons one. A hotfix: `sugar hotfix OWNER/REPO start` (a `hotfix` branch from `main`), fix PRs branched from `origin/hotfix`, into `hotfix`, merged as usual, then `sugar hotfix OWNER/REPO open`; after the user's merge Sugarhouse finishes it and carries the fix into `rc`. Don't tag by hand there.
- Run every tool through mise: `mise exec -- cargo test --workspace --locked`, `mise exec -- go test ./...`, `mise exec -- mix precommit` (or `mix test` and `mix compile --warnings-as-errors`), `mise exec -- gh release view vX.Y.Z`.
- **GitOps repositories** (a repository Argo CD syncs from, such as breakdown-infra): a release is the repository's own path, and its README's *Releasing* section is the procedure. Its hand-run steps (an Argo sync, a hard refresh) are the user's, and one that must follow a merge goes in that merge's task. In breakdown-infra:
  1. **Before staging,** list the migrations the release adds: the app repository's migration files changed between the commit production runs and the one you stage. Each image is tagged with its commit, so read production's commit from the GitHub package version that holds production's pinned digest. The App can't read packages; pass the `read:packages` token `stage.sh` already uses (that use needs no `--as-owner` ask) by environment, never printed and never by widening the login: `GH_TOKEN="$(<~/.config/breakdown/ghcr-read-token)" mise exec -- gh api --paginate '/orgs/Applesauce-Labs/packages/container/IMAGE/versions?per_page=100' --jq '.[] | select(.name == "DIGEST") | .metadata.container.tags[]'` prints that digest's tags, one of them the commit. If the token file is missing, making it is the user's step (README *Releasing* links it). Migrations run in PreSync hook Jobs pinned to the digest, in admin's own container at start, and in sales' and support-phone's init containers, so the guard hook sees none of them.
  2. **`scripts/stage.sh IMAGE[@SHA]`** opens the staging PR. Add the migrations it carries to the PR (`mise exec -- gh pr comment`), naming any contract or destructive one: dropping a column or table, or deleting data. A staging-only PR is yours to squash-merge once green (`mise exec -- gh pr merge <full PR URL> --squash`); one carrying a destructive migration first waits for the user's yes, asked as a critical board item.
  3. **Check staging:** once Argo shows staging Synced and Healthy, check the release there (`<app>-staging.<tailnet>.ts.net`) and say what you checked.
  4. **`scripts/promote.sh IMAGE`** opens the production PR. List every migration it carries since production's commit, from every stage PR it collects, in a comment on the PR and in its merge task, with any destructive one named first. The user approves and merges it. Argo deploys it and reports to the user's phone; read the result from Argo, read-only.
  5. **Rollback** is reverting the promotion PR, handed over the same way. A revert doesn't undo a migration: the previous release has to run on the new schema, which is why migrations are written expand/contract.

  `stage.sh` and `promote.sh` open ready, digest-only PRs that get no draft or review loop; breakdown-infra's AGENTS.md counts them apart from the one-open-PR rule. Never run a migration Job, restart, scale or sync by hand there. With read-only cluster access, that's the only way, and a refusal means the step is the user's or a PR's, never a different command.
- **Phoenix / Elixir:** read the version from `project/0` in `mix.exs` or the source it references. Apps that bake `@version Mix.Project.config()[:version]` need a rebuild after the bump. When the app uses database migrations and is deployed by hand (not through a GitOps repository), every release runs the migration procedure before the app restarts: read [references/phoenix-migrations.md](references/phoenix-migrations.md) and follow it exactly. A destructive migration waits for the user's yes.
- **Go with GoReleaser:** use the `ldflags` symbols the application actually declares (`-X main.Version={{.Version}}` and the like). A released binary that prints `dev` means the build's `ldflags` or version source is wrong.
