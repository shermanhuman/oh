Oh (Sherman's working agreements) is installed. In every session:

**Mise first.** Mise is the CLI tool and runtime manager. Check `mise which <tool>` or `mise ls` before installing anything, and never use `apt`, `brew`, `npm install -g`, `go install` or `pip install` for tools mise provides (per-project dependencies are exempt). Install with `mise install` / `mise use <tool>@<version>` (`--global` only for intended user-wide installs; keep project pins). Without shell activation, run tools as `mise exec -- <command>`. GitHub always goes through `mise exec -- gh`, including PRs, never a browser for what `gh` supports. For other services use a connected MCP server when it covers the operation, otherwise the CLI through mise. Fall back only when mise can't provide the tool, and say why.

**Pull requests are releases.** A PR is a build, a version bump and a rollout. Batch the work, finish and test it locally, then open one PR per repository; while yours is open, push to its branch (check it's still open first) instead of opening another. Others' open PRs don't block yours. Until the PR, work in a separate git worktree on a feature branch; the main checkout may hold someone else's work or dev servers (reading there, or running a requested command, is fine). Run tests the way CI does and check user-facing changes end to end, locally, so the PR starts green. Reviews follow `compound-v:review-loop`, with every round and its fix notes posted on the PR. The user merges, because each merge starts a release: never merge a PR or push to the default branch. Merge the default branch into your branch when it moves; don't rebase or force-push, so SHAs posted on the PR stay valid. The procedure is in the `oh:pull-requests` skill.

**Version bumps.** Every PR in a repository with a plugin manifest, `mix.exs` or `go.mod` carries a version bump (one per changed plugin where a repository holds several), even where CI doesn't check: patch for fixes and docs, minor for compatible features, major for breaking changes, unless the user names a level. Bump last, after testing and review, from the PR base's version, using the `oh:release` skill; if another PR merges first and the base reaches your version, re-apply the same level. A bump never authorizes tagging, publishing, merging or deploying.

**Reviewers.** In Claude Code, reviewer and plan-review subagents run on model `fable` at high effort. The second voice for the review loop's independent pass, and any "Astra" review the user asks for, is Astra high through Codex, run in the background with the brief on stdin:
`codex exec -m gpt-6-astra -c model_reasoning_effort=high -s read-only --skip-git-repo-check -C <dir> -o <out.md> - < brief.md`
Tell Astra which skill to use (`compound-v:review`, `compound-v:followup` or `compound-v:plan-review`), the diff range or plan, and the facts already verified. Its sandbox can't post or call MCP tools, so post its report on the PR or issue yourself, unchanged, under an "Astra high (Codex)" header. Don't add `--dangerously-bypass-hook-trust`. If Codex fails or is unavailable, fall back as the review loop says and note it on the PR. When you are the Codex session: a fresh reviewer is a separate background `codex exec` with the brief on stdin, and the second voice is Claude (`claude -p --model fable` with the brief on stdin) when it's installed, otherwise the review loop's fallback.
