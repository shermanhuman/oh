Oh (Sherman's working agreements) is installed. In every session:

**Mise first.** Install and run CLI tools through mise (`mise which`, `mise use`, `mise exec --`), never `apt`, `brew`, `npm install -g`, `go install` or `pip install` for tools mise provides. GitHub always goes through `mise exec -- gh`. Details: `oh:mise`.

**Pull requests** follow `compound-v:pull-requests` and `compound-v:release`; this machine's specifics (the second voice, installs on both machines, Codex hook trust) are in `oh:pull-requests` and `oh:release`.

**Production guard.** Merging a PR, pushing to a default branch, force-pushing, pushing every branch and deleting a repository are the user's, with one exception: where Sugarhouse has set a repository up with `rc` (`sugar repo setup`), you squash-merge your own green PR into `rc` or `hotfix` yourself, as `gh pr merge <full PR URL> --squash` through Sugarhouse's wrapper, which checks it with the board. Otherwise these are the user's: hand them the exact command as a task (`compound-v:interrogate`'s *Tasks for the human*), with only its link in the chat (the user acts where the command is). These production actions wait for their yes: deleting, draining, cordoning or scaling to zero on a cluster that isn't local, `helm uninstall`, destructive SQL on a database that isn't local, and deleting cloud resources (buckets, DNS records, VMs, managed databases) in an account that isn't local. Where the guard hook can't ask for it (cloud deletes, a destructive migration inside a release Job, anything in Codex), a production action is also a task with the exact command for the user to run; an answer to a question never authorizes you to run it. A guard hook enforces both lists for shell commands, except cloud deletes; the rule also covers interpreter code, MCP tools and port-forwarded databases. The release routine goes ahead without asking: in a GitOps repository it's the repository's own path (in breakdown-infra, `scripts/stage.sh` then `scripts/promote.sh`, whose PRs the user merges), otherwise rollout restarts, Argo refreshes, migration Jobs and deploy scripts. A destructive change inside it (a migration that drops a column or table, or deletes data) still waits for their yes: check the release's pending migrations before you stage or run it, since the hook can't see inside a Job, a sync hook or a container; in a GitOps release, name it in the PR and its merge task, and the user's merge is their yes. Where your cluster access is read-only, a release is a PR, never a way around that access (`oh:release`). Never loosen a grant, role or allowlist to get past a block (compound-v's always-on covers merging, rebasing and refusals).

**Messages that leave.** A message owning our error to a customer, partner or vendor is short, owns it without internal mechanics (job names, endpoints, timestamps) or security posture (which environment held which credentials), and asks for the least that fixes it. A support ticket about their failure keeps the facts they need to act.

**Secrets.** In a repository with `.waxseal/`, every secret change is one visible waxseal command (`oh:waxseal`): no `kubeseal`, hand-written `encryptedData` or Secret Manager access another way; if waxseal can't do it, ask the user. Never print a file that holds secrets, even filtered, by any tool (shell, the Read tool, code); to see what an env file holds, list its uppercase key names (`grep -oE '^[A-Z_][A-Z0-9_]*=' FILE`), and pass secrets by path or environment variable.

**Processes.** Other sessions share the machine: kill one process you started per command (`kill <pid>`), never by name or pattern. A guard hook refuses pattern kills and printing secret files in shell commands.

**No silent failures.** Never ship a change that makes something fail silently for some users; when a fix removes a fallback, find out who relied on it.

**Reviewers.** In Claude Code, a round that reviews the whole diff (`compound-v:review`, at any tier) and a plan's first `compound-v:plan-review` run on `fable` at high effort, except the second voice's. A `compound-v:followup` round, and a plan re-review after revisions, run on `opus` at high effort; this replaces compound-v's "no lower model and effort than round 1" for those. The exception is a follow-up the review loop gives the second voice: the second voice runs it, or, when it's unavailable, a fresh reviewer at round 1's model and effort. A revision that changes the plan's scope or approach gets a first review again. On production-safety and release-path work (the production guard, the release routine or `oh:release`, deploy scripts, migrations) there's no round cap or six-round guard: keep going until a round finds no must-fix, and tell reviewers there's no last round (the spinning rule still applies). The second voice, and any "Astra" review, is Astra high through Codex (command in `oh:pull-requests`); in a Codex session it's Claude Fable. Any reviewer due on Fable that finds it unavailable (a 429, or its weekly cap), the Codex session's second voice and a stand-in included, runs on `opus` at high effort instead, and its report says so.
