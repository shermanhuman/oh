Oh (Sherman's working agreements) is installed. In every session:

**Mise first.** Mise is the CLI tool and runtime manager. Check `mise which <tool>` or `mise ls` before installing anything, and never use `apt`, `brew`, `npm install -g`, `go install` or `pip install` for tools mise provides (per-project dependencies are exempt). Install with `mise install` / `mise use <tool>@<version>` (`--global` only for intended user-wide installs; keep project pins). Without shell activation, run tools as `mise exec -- <command>`. GitHub always goes through `mise exec -- gh`, including PRs, never a browser for what `gh` supports. For other services use a connected MCP server when it covers the operation, otherwise the CLI through mise. Fall back only when mise can't provide the tool, and say why.

**Pull requests are releases.** A PR is a build, a version bump and a rollout. Batch the work, finish and test it locally, then open one PR per repository; while yours is open, push to its branch (check it's still open first) instead of opening another. Others' open PRs don't block yours. Until the PR, work in a separate git worktree on a feature branch; the main checkout may hold someone else's work or dev servers (reading there, or running a requested command, is fine). Run tests the way CI does and check user-facing changes end to end, locally, so the PR starts green. Reviews follow `compound-v:review-loop`, with every round and its fix notes posted on the PR. The user merges, because each merge starts a release: never merge a PR or push to the default branch. Merge the default branch into your branch when it moves; don't rebase or force-push, so SHAs posted on the PR stay valid. The procedure is in the `oh:pull-requests` skill.

**Watch your pull requests.** A PR you opened is yours to keep mergeable and green until the user merges it; the user shouldn't be the one who finds a conflict or a red check. After every push, watch its checks in the background and fix failures before calling it ready. Before telling the user anything is ready to merge, and whenever you come back to a session with open PRs, check each one's mergeability and checks. When another PR merges into the base, the merge and re-bump rules here apply; then watch again. A PR leaves draft only when the user could merge it right now: its base is the default branch, it is mergeable and up to date with that branch, every check is green, the review loop's last round is clean and the bump has landed. A PR stacked on another PR's branch stays a draft until that PR merges and yours is retargeted to the default branch. When a ready PR stops meeting this (the base moved, or a check went red), put it back to draft until it does. Say what you fixed. The commands are in the `oh:pull-requests` skill.

**Version bumps.** Every PR in a repository with a plugin manifest, `mix.exs`, `go.mod` or `Cargo.toml` carries a version bump (one per changed plugin where a repository holds several; a PR that touches no plugin bumps nothing), even where CI doesn't check: patch for fixes and docs, minor for compatible features, major for breaking changes, unless the user names a level. Bump last, after testing and review, from the PR base's version, using the `oh:release` skill; if another PR merges first and the base reaches or passes your version, re-apply the same level. A bump never authorizes tagging, publishing, merging or deploying.

**Sealed secrets go through waxseal.** Every secret change is a waxseal command: `waxseal key add|set|edit`, `waxseal reseal`, `waxseal secret list|show|retire`, run one visible command per call, with values from `--from-file`, stdin, `--generate`, or `--from-key` for a value waxseal already stores. Don't wrap waxseal in a generated script, seal with `kubeseal`, hand-write `encryptedData`, or read or write Google Secret Manager another way (`gcloud secrets`, the REST API, the client library); waxseal's metadata stays true only when every change goes through it. If waxseal can't do what's needed, stop and ask the user instead of working around it. If gcloud needs a fresh login, ask the user to run `! gcloud auth login`. A guard hook refuses `kubeseal`, `gcloud secrets` commands other than `list`, `describe`, `get-iam-policy`, `versions list|describe` and `locations`, and Secret Manager URLs given to curl or wget; it doesn't read code, so the rule alone covers client libraries and wrapper scripts. The commands are in the `oh:waxseal` skill.

**Production guard.** Some steps are always the user's: merging a pull request (by `gh pr merge`, `gh api` or GraphQL), pushing to a default branch, force-pushing (`--force`, `--force-with-lease`, `+refspec`), pushing every branch, and deleting a repository. Don't run them; say what you wanted to do and hand the user the exact command. Irreversible production actions wait for the user's yes: `kubectl delete`, `drain`, `cordon` or scaling to zero on a cluster that isn't local, `helm uninstall`, and DROP, TRUNCATE, ALTER TABLE ... DROP or DELETE without WHERE against a database that isn't local, including one reached through `kubectl exec`, ssh or a port-forward. A guard hook refuses the first group and asks the user about the second (in Codex, which can't ask from a hook, it refuses both). It reads only shell commands, so the rule alone covers interpreter code, port-forwarded databases and anything the hook can't parse. Never route around a refusal. The release routine (rollout restarts, Argo refreshes, migration Jobs, deploy scripts) is not guarded.

**Questions.** Respect the user's time: research everything first, then ask it all at once as one decision packet (`compound-v:interrogate`), never one question after another. Show, don't tell: put the mock, diagram, diff or example output in front of the user instead of describing it. Everything needed to decide sits inside the packet itself, because a question widget hides text written before it. Recommendation first, so `ok` accepts it; every decision ends with a **More discussion** option. Walkthroughs for the user (release reviews, PR summaries, design rounds) follow the same rule: one pass, showing what changed. If the user asks to talk instead of choosing, talk it through in prose until they ask for choices again.

**Rough edges.** Log each one as a comment on [Applesauce-Labs/factory#8](https://github.com/Applesauce-Labs/factory/issues/8), first line `rough-edge: <skill or rule> · <kind> · <link>`, then what was missing or went wrong. Log: a More discussion pick, a follow-up packet the first could have covered, an override the research could have predicted, a correction from the user, a step the user had to do by hand, a skill that should have run and didn't, a problem a review or check should have caught, and work stopped after failed rounds.

**Reviewers.** In Claude Code, reviewer and plan-review subagents run on model `fable` at high effort. The second voice for the review loop's independent pass, and any "Astra" review the user asks for, is Astra high through Codex, run in the background with the brief on stdin:
`codex exec -m gpt-6-astra -c model_reasoning_effort=high -s read-only --skip-git-repo-check -C <dir> -o <out.md> - < brief.md`
Tell Astra which skill to use (`compound-v:review`, `compound-v:followup` or `compound-v:plan-review`), the diff range or plan, and the facts already verified. Its sandbox can't post or call MCP tools, so post its report on the PR or issue yourself, unchanged, under an "Astra high (Codex)" header. Don't add `--dangerously-bypass-hook-trust`. If Codex fails or is unavailable, fall back as the review loop says and note it on the PR. When you are the Codex session: a fresh reviewer is a separate background `codex exec` with the brief on stdin, and the second voice is Claude (`claude -p --model fable` with the brief on stdin) when it's installed, otherwise the review loop's fallback.
