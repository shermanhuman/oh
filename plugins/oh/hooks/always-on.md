Oh (Sherman's working agreements) is installed. In every session:

**Mise first.** Mise is the CLI tool and runtime manager. Check `mise which <tool>` or `mise ls` before installing anything, and never use `apt`, `brew`, `npm install -g`, `go install` or `pip install` for tools mise provides (per-project dependencies are exempt). Install with `mise install` / `mise use <tool>@<version>` (`--global` only for intended user-wide installs; keep project pins). Without shell activation, run tools as `mise exec -- <command>`. GitHub always goes through `mise exec -- gh`, including PRs, never a browser for what `gh` supports. For other services use a connected MCP server when it covers the operation, otherwise the CLI through mise. Fall back only when mise can't provide the tool, and say why.

**Pull requests are releases.** A PR is a build, a version bump and a rollout. Batch the work, finish and test it locally, then open one PR per repository; while yours is open, push to its branch (check it's still open first) instead of opening another. Others' open PRs don't block yours. Until the PR, work in a separate git worktree on a feature branch; the main checkout may hold someone else's work or dev servers (reading there, or running a requested command, is fine). Run tests the way CI does and check user-facing changes end to end, locally, so the PR starts green. Reviews follow `compound-v:review-loop`, with every round and its fix notes posted on the PR. The user merges, because each merge starts a release: never merge a PR or push to the default branch. Merge the default branch into your branch when it moves; don't rebase or force-push, so SHAs posted on the PR stay valid. The procedure is in the `oh:pull-requests` skill.

**Watch your pull requests.** A PR you opened is yours to keep mergeable and green until the user merges it; the user shouldn't be the one who finds a conflict or a red check. After every push, watch its checks in the background and fix failures before calling it ready. Before telling the user anything is ready to merge, and whenever you come back to a session with open PRs, check each one's mergeability and checks. When another PR merges into the base, the merge and re-bump rules here apply; then watch again. Say what you fixed. The commands are in the `oh:pull-requests` skill.

**Version bumps.** Every PR in a repository with a plugin manifest, `mix.exs` or `go.mod` carries a version bump (one per changed plugin where a repository holds several; a PR that touches no plugin bumps nothing), even where CI doesn't check: patch for fixes and docs, minor for compatible features, major for breaking changes, unless the user names a level. Bump last, after testing and review, from the PR base's version, using the `oh:release` skill; if another PR merges first and the base reaches or passes your version, re-apply the same level. A bump never authorizes tagging, publishing, merging or deploying.

**Sealed secrets go through waxseal.** Every secret change is a waxseal command: `waxseal key add|set|edit`, `waxseal reseal`, `waxseal secret list|show|retire`, run one visible command per call, with values from `--from-file`, stdin or `--generate`. Don't wrap waxseal in a generated script, seal with `kubeseal`, hand-write `encryptedData`, or read or write Google Secret Manager another way (`gcloud secrets`, the REST API, the client library); waxseal's metadata stays true only when every change goes through it. If waxseal can't do what's needed, stop and ask the user instead of working around it. If gcloud needs a fresh login, ask the user to run `! gcloud auth login`. A guard hook refuses `kubeseal`, `gcloud secrets` commands other than `list`, `describe`, `get-iam-policy`, `versions list|describe` and `locations`, and Secret Manager URLs given to curl or wget; it doesn't read code, so the rule alone covers client libraries and wrapper scripts. The commands are in the `oh:waxseal` skill.

**Production guard.** Some steps are always the user's: merging a pull request (by `gh pr merge`, `gh api` or GraphQL), pushing to a default branch, force-pushing (`--force`, `--force-with-lease`, `+refspec`), pushing every branch, and deleting a repository. Don't run them; say what you wanted to do and hand the user the exact command. Irreversible production actions wait for the user's yes: `kubectl delete`, `drain`, `cordon` or scaling to zero on a cluster that isn't local, `helm uninstall`, and DROP, TRUNCATE, ALTER TABLE ... DROP or DELETE without WHERE against a database that isn't local, including one reached through `kubectl exec`, ssh or a port-forward. A guard hook refuses the first group and asks the user about the second (in Codex, which can't ask from a hook, it refuses both). It reads only shell commands, so the rule alone covers interpreter code, port-forwarded databases and anything the hook can't parse. Never route around a refusal. The release routine (rollout restarts, Argo refreshes, migration Jobs, deploy scripts) is not guarded.

**Questions.** Put everything the user needs to decide inside the question itself, never only in text before it: the question widget hides that text. Say what the decision is, why it matters, a concrete example, the trade-offs of each option and your recommendation, with the situation in the question text, each option's consequence in its description, and longer detail in a per-option preview where the host has one, otherwise in the question text. Keep each question self-contained, and ask one decision per question when the topic is unfamiliar. If the user rejects a question "to clarify", ask in plain text what they want clarified instead of showing another widget; if they ask for a conversation instead of multiple choice, talk it through in plain text until they ask for choices again.

**Reviewers.** In Claude Code, reviewer and plan-review subagents run on model `fable` at high effort. The second voice for the review loop's independent pass, and any "Astra" review the user asks for, is Astra high through Codex, run in the background with the brief on stdin:
`codex exec -m gpt-6-astra -c model_reasoning_effort=high -s read-only --skip-git-repo-check -C <dir> -o <out.md> - < brief.md`
Tell Astra which skill to use (`compound-v:review`, `compound-v:followup` or `compound-v:plan-review`), the diff range or plan, and the facts already verified. Its sandbox can't post or call MCP tools, so post its report on the PR or issue yourself, unchanged, under an "Astra high (Codex)" header. Don't add `--dangerously-bypass-hook-trust`. If Codex fails or is unavailable, fall back as the review loop says and note it on the PR. When you are the Codex session: a fresh reviewer is a separate background `codex exec` with the brief on stdin, and the second voice is Claude (`claude -p --model fable` with the brief on stdin) when it's installed, otherwise the review loop's fallback.
